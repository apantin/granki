# Как вносить изменения

Порядок работы над самим Granki: как проверять правки на своей серии, какие тесты запускать и что обновить вместе с изменением. Выпуск версии описан в [release.md](release.md).

## Рабочее место

Удобнее всего проверять Granki сразу на живой серии. Для этого в проект с серией скиллы подключаются символическими ссылками на рабочую копию Granki, а не копируются установщиком. Тогда правка в копии действует сразу, переустанавливать ничего не нужно.

1. Поставь в проект ядро BMad, оно нужно для комнат:
   ```bash
   npx bmad-method@6.12.4 install --directory . --modules core --tools claude-code,codex --yes
   ```
2. Подключи скиллы ссылками и поставь комнаты (`GRANKI` — путь к рабочей копии):
   ```bash
   GRANKI=~/work/granki
   mkdir -p .claude/skills .agents/skills
   for s in "$GRANKI"/skills/granki-*; do
     ln -sfn "$s" .claude/skills/; ln -sfn "$s" .agents/skills/
   done
   uv run .claude/skills/granki-tools/scripts/rooms.py install --project-root .
   ```
3. Не коммить ссылки в репозиторий проекта: они указывают на пути твоей машины. Добавь в его `.gitignore`:
   ```
   .claude/skills/granki-*
   .agents/skills/granki-*
   ```

Скрипты читаются заново при каждом запуске. `SKILL.md` агент читает при старте сессии, поэтому после его правки начни новую сессию. После правки `party-rooms.toml` снова запусти `rooms.py install`.

Пока ты меняешь Granki, держи серию в отдельной ветке её репозитория. Тогда неудачный эксперимент можно выбросить вместе с веткой. В журнал статьи полезно записать, на каком коммите Granki шла работа, например `journal.py log --action "granki 1a2b3c4"`: так потом понятно, какой версией сделано ревью.

Проверить упаковку, то есть то, что получит пользователь, можно установкой из рабочей копии в пустую папку. Команды — в [release.md](release.md#перед-выпуском).

## Тесты

```bash
uv run --no-project --with pyyaml python -m unittest discover -s skills/granki-tools/scripts/tests
```

Тесты HTML и туториала нужны Pandoc: из `PATH` или из переменной `GRANKI_PANDOC`. Без него эти тесты пропускаются, и в итоге видно `skipped`.

| Файл | Что проверяет |
|---|---|
| `test_scripts.py` | Поведение каждого скрипта на маленькой вымышленной серии (`fixture.py`) |
| `test_regressions.py` | Ошибки, которые уже находили: на каждую по тесту |
| `test_tutorial.py` | Выполняет все команды из [туториала](../user/tutorial.md) и сверяет вывод с тем, что показано в тексте |
| `test_readme.py` | Каждый `.md` есть в оглавлении README, кроме материалов примеров внутри `docs/example/<пример>/`; относительные ссылки во всех `.md` ведут на существующие файлы |
| `test_version.py` | Номер версии совпадает в `module.yaml`, `marketplace.json`, README и `CHANGELOG.md` |

## Что обновить вместе с изменением

| Если изменилось | Что обновить |
|---|---|
| Найдена и исправлена ошибка | Добавь тест в `test_regressions.py`: он должен падать без исправления |
| Вывод или поведение скрипта | Туториал и пример `docs/example/bread/`. Пример обновляй прогоном скриптов, а не руками. Если вывод разошёлся с текстом туториала, `test_tutorial.py` упадёт |
| Формат файлов серии | Сначала [formats.md](../../skills/granki-tools/references/formats.md) — основной документ по форматам, потом шаблоны в `assets/templates/` и пример. Такое изменение несовместимо, см. [release.md](release.md#номер-версии) |
| Порядок работы, статусы, роли | [process.md](../user/process.md) или [roles.md](../user/roles.md) и скиллы, которые этот порядок выполняют |
| Состав модуля: скиллы, скрипты, раскладка | [architecture.md](architecture.md), таблицы в README, `marketplace.json` и `module-help.csv` при новом скилле |
| Существенный выбор с альтернативами | Новый ADR в [decisions/](decisions/) |
| Новый `.md` файл | Оглавление README, иначе упадёт `test_readme.py` |
| Что угодно заметное для пользователя | Строка в разделе «Не выпущено» в [CHANGELOG.md](../../CHANGELOG.md) |

## Документация

- `docs/user/` — как пользоваться Granki: туториал, процесс, роли, конфликты с другими скиллами.
- `docs/dev/` — как Granki устроен и развивается: замысел, устройство, решения, история, планы, этот файл и порядок выпуска.
- Справочники для агента лежат в `references/` своего скилла.

Каждое правило описывается в одном документе, остальные на него ссылаются. Пересказ в одну строку допустим, вторая копия правила — нет.

Скиллы пишутся по стандарту bmad-builder: `SKILL.md` короткий и описывает результат, подробности — в `references/`, всё, у чего есть один правильный ответ, делают скрипты. Префикс скиллов — `granki-`: префикс `bmad-` зарезервирован за BMad, правила товарного знака описаны в [architecture.md](architecture.md).

## Приватность

Granki проверяется на настоящих сериях, но в репозиторий попадает только обобщённое:
- примеры в документации, тестах и `docs/example/` вымышленные;
- данные, тексты и рукописи серий, на которых проверялся Granki, в репозиторий не входят;
- итоги проверок на живом материале описываются без чисел и формулировок из этих серий, как в [history.md](history.md);
- в документах не упоминаются локальные пути, адреса почты и имена людей.

Перед коммитом посмотри состав изменений (`git diff --cached --stat`) и прогони поиск локальных путей и адресов из [release.md](release.md#перед-выпуском).
