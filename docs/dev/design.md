# Замысел и принятые решения

## Зачем

Когда агент пишет статью целиком и сам же её проверяет, автор получает длинный текст чужим голосом, с числами, которые надо перепроверять вручную, и с пакетами из десятков замечаний. Опыт первой серии ([уроки](lessons.md)) показал три источника переделок:
- агент не знает того, что знает только автор;
- редактура вносит чужой голос;
- автору приходится вычитывать статью целиком.

Granki превращает подготовку серии в повторяемый процесс:
- план отделён от текста и пишется для чтения человеком;
- текст пишется и принимается по разделам;
- агенты проверяют на трёх уровнях: раздел, статья, серия;
- роли агентов спорят, а решает автор;
- числа проверяют скрипты;
- статусы публикации защищают уже вышедшие статьи.

Нормативное описание — в [process.md](../user/process.md), роли — в [roles.md](../user/roles.md), устройство модуля — в [architecture.md](architecture.md).

## Принятые решения

| Решение | Альтернатива | Причина |
|---|---|---|
| План и реализация хранятся раздельно. План написан для чтения и обсуждения человеком | Сразу писать текст статьи | Автор вычитывает и перестраивает план до текста; перестройка плана не требует переписывать готовые разделы вслепую |
| Единица работы — раздел статьи | Писать и ревьюить статью целиком | Один раздел легко прочитать и прокомментировать, работа атомарнее |
| Ревью агентами на трёх уровнях: раздел, статья, серия | Только итоговое ревью | Мелкие проблемы ловятся в разделе, связность — в статье, согласованность — в серии |
| Основа — BMad Method **v6.12** (`party-mode`, `review`, `help`, установщик) | BMad v7, свои скиллы без BMad | v7 в preview alpha, ожидаются ломающие изменения; в v6.12 есть все нужные механизмы. Подробно — [ADR 0001](decisions/0001-bmad-v6-foundation.md) |
| Редакторское знание redaktura-skills **копируется и адаптируется** в собственный скилл | Зависимость от плагина | Нужна стабильность и адаптация под жанр; лицензия CC BY 4.0 это разрешает с указанием авторства |
| Ролевые обсуждения не принимают решений. Итог — вопросы автору по одному | Голосование комнаты | Решения остаются за автором; обсуждение одной моделью склонно к лёгкому согласию |
| Название **Granki** (гранки), префикс скиллов `granki` | Redkollegia, Planerka, Vychitka, Draftsmith и другие | Название описывает главную идею — вычитку по частям до сборки; короткое и свободно в npm |
| Отдельный открытый репозиторий; код под MIT, справочники редактуры под CC BY 4.0 | Разработка внутри проекта с первой серией, Apache-2.0 | Открытому проекту нужна собственная история и лицензия |
| Планы: сначала автор, затем агенты. Текст: сначала агенты, затем автор | Единый порядок для всех уровней | Замысел задаёт автор, а агенты проверяют согласованный план. В тексте агенты заранее убирают механические ошибки, и автор читает только содержание |
| Канон (редакционные правила): слой проекта с перекрытием на уровне серии и статьи | Один канон на проект | У серии и отдельной статьи бывают свои читатель, регистр и словарь |
| После ревью агент предлагает четыре варианта: применить все, обсудить по одной, применить только критичные, записать и отложить | Агент применяет правки сам | Автор решает, сколько времени тратить сейчас; отложенное не теряется |
| Журнал статьи `journal.md`: реестр находок со сквозными ID и хронология действий; memlog BMad не используется | memlog BMad рядом с каждым артефактом | Хронология и находки статьи в одном читаемом месте, к которому возвращаются в следующей сессии |
| Числа проверяют скрипты, не агенты | Проверка чисел LLM-ревьюером | Урок PaperOrchestra и первой серии: скрипт сверяет сотни значений без ошибок, агент — нет |
| Скилл остаётся, только пока он лучше голой модели | Наращивать шаги впрок | Стандарт bmad-builder; после пилота шаги, комнаты и линзы, не изменившие результат, убираются |

Существенные решения с альтернативами оформляются в [decisions/](decisions/).
