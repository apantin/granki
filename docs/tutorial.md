# Туториал: статья от плана до публикации

Туториал проводит одну статью через весь цикл Granki на вымышленной серии «Хлеб на закваске». Автор испёк шесть буханок: три вида муки, две расстойки. Пробовали их 12 гостей. Файлы серии лежат в [examples/bread/](../examples/bread/).

Туториал состоит из двух частей:
1. **Как появились файлы примера.** Что автор говорит агенту на первых шагах и что получается. Эту часть достаточно прочитать.
2. **Дальше руками.** Раздел, ревью, решение по находкам, приёмка, публикация и новая версия. Здесь вы запускаете те же скрипты, которые скиллы вызывают под капотом, и видите их настоящий вывод.

В работе вы разговариваете с агентом, а скрипты запускает он. Ручной запуск показывает, на чём держится процесс: что проверяется автоматически, где хранятся решения и почему записанное решение не теряется между сессиями.

## Словарь

| Слово | Что значит |
|---|---|
| План | Файл `plan.md` статьи или `series-plan.md` серии. Тело плана читает человек, фронтматтер — скрипты |
| Фронтматтер | Блок YAML между строками `---` в начале файла: статус, разделы, правила проверки |
| Раздел | Файл `NN-имя.md` в папке `sections/`. Единица письма, ревью и приёмки |
| Утверждение | Строка таблицы `data/claims.csv`: ID, формулировка, значение и источник. На утверждения опирается каждое число в тексте |
| Опора | Ссылка из плана на утверждение, например `[B-wheat-12-liked]` |
| Локатор | Адрес значения в исходных данных: `bake.csv: flour_id=wheat; hours=12; column=liked` — строка таблицы по условиям и колонка; `setup.json#/tasters` — поле JSON (запись JSON Pointer) |
| Оговорка | Обязательная фраза с ID (C1, C2). В тексте её отмечает метка `<!-- caveat:C1 -->`, и формулировку можно свободно редактировать |
| Линза | Одна независимая проверка в ревью: редактура, опора на данные, свежий читатель, структура. Каждая линза — отдельный субагент со своим отчётом |
| Находка | Замечание линзы: ID, важность, вид, цитата, предложение и статус. Хранится в журнале |
| Журнал | `journal.md` статьи или серии: реестр находок и хронология действий |
| Комната | Обсуждение с ролями агентов в `bmad-party-mode`, например фокус-группа читателей. Комната не решает, а задаёт вопросы автору |

## Что нужно

- Python 3.11+, доступный как `python3`. На macOS системная заглушка `python3` без Command Line Tools не подойдёт.
- [uv](https://docs.astral.sh/uv/).
- [Pandoc](https://pandoc.org/) в `PATH` или в переменной `GRANKI_PANDOC` — только для шага 9.
- Для работы с агентом — ядро BMad Method v6 и установленный Granki (см. [README](../README.md#установка)). Для этого туториала они не нужны.

## Часть 1. Как появились файлы примера

```
examples/bread/
  .agents/redpolitika.md              редполитика проекта
  articles/bread/
    series-plan.md  journal.md        план серии и её журнал
    author-notes.md  redpolitika.md   заметки автора и слой редполитики серии
    01-flour/
      plan.md  journal.md             план статьи и её журнал
      data/bake.csv  data/setup.json  исходные данные
      data/claims.csv                 таблица утверждений
      sections/00-intro.md …          разделы
```

### Шаг 1. Серия

Автор зовёт Главреда:

> Главред, хочу серию про хлеб на закваске: что я выяснил на своей кухне.

Главред видит, что серии ещё нет, и передаёт работу `granki-series`. Скилл расспрашивает о читателе, жанре и о том, чего серия не касается, и готовит черновик [series-plan.md](../examples/bread/articles/bread/series-plan.md) в статусе `draft`. Автор читает план и правит его вместе с агентом: например, переносит подкормку закваски во вторую статью. Потом план проверяют агенты, и автор утверждает его командой `plan.py series --set approved`. Это записано в [журнал серии](../examples/bread/articles/bread/journal.md). В примере ревью планов опущено, поэтому отчётов о нём нет.

У статьи `02-starter` нет плана. Такая статья считается `planned`: она есть в замысле, но работа над ней не начата.

### Шаг 2. Интервью и данные

`granki-intake` задаёт автору вопросы по одному и записывает ответы в [author-notes.md](../examples/bread/articles/bread/author-notes.md) с пометками:
- `[автор]` — это сказал автор;
- `[подтверждено]` — сверено с данными;
- `[проверить]` — пока не сверено.

Агент не додумывает, как шёл эксперимент. Например, то, что гости пробовали вслепую, записано со слов автора.

Затем из данных строится таблица утверждений. Правило `claims_build` в плане статьи превращает в утверждения колонки `rise` (во сколько раз поднялось тесто) и `liked` (доля гостей, которым понравилось) для каждой строки `bake.csv`: 12 утверждений с ID и локаторами. Ещё две строки, `B-tasters` и `B-long`, заведены вручную и ссылаются на `setup.json`.

```
B-wheat-12-liked,"пшеничная, 12 ч: liked",0.75,bake.csv: flour_id=wheat; hours=12; column=liked
B-tasters,Число гостей,12,setup.json#/tasters
```

### Шаг 3. План статьи

`granki-article-plan` пишет [plan.md](../examples/bread/articles/bread/01-flour/plan.md).

Тело плана — для человека. В нём вопрос читателя, тезис и разделы. У каждого раздела указаны назначение, тезисы, опоры, оговорки и переход к следующему.

Фронтматтер — для скриптов:
- объём;
- правила чисел: `percent:0` разрешает писать `0.75` в тексте как «75», `fixed:1` — `2.1` как «2,1»;
- обязательные оговорки C1 и C2;
- записи разделов.

Автор читает план до того, как написан текст. Когда план утверждён, `granki-section` пишет разделы. Журнал статьи хранит всю цепочку:

```
- … · агент · 01-results.md · в план добавлен раздел; оговорки: C2; опоры: B-wheat-12-rise, …
- … · автор · статус статьи: plan-draft → plan-approved
- … · агент · статус статьи: plan-approved → writing
- … · агент · 01-results.md · раздел: planned → drafted
```

На этом пример остановлен: три раздела написаны и ждут ревью. Дальше работаете вы.

## Часть 2. Дальше руками

### Подготовка

Выполняйте все шаги в одном окне терминала: переменные, функция и текущая папка переходят от шага к шагу. Начните из корня репозитория Granki и скопируйте пример во временную папку, чтобы не менять репозиторий.

```bash
GRANKI=$PWD
WORK=$(mktemp -d)
cp -r examples/bread "$WORK/"
cd "$WORK/bread/articles/bread"
gr() { uv run -q "$GRANKI/skills/granki-tools/scripts/$1.py" "${@:2}"; }
```

`gr check …` — сокращение для `uv run -q "$GRANKI/skills/granki-tools/scripts/check.py" …`. Функция работает в bash и zsh. Даты и время в журналах у вас будут свои.

### Шаг 4. Где мы

Это первое, что делает Главред в каждой сессии.

```bash
gr status --series series-plan.md --format md
```

```
# Хлеб на закваске

План серии: writing. Нерешённые находки серии: 0 (критичных 0).

| Статья | Статус | Разделы | Изменены после приёмки | Устаревшие ревью | Нерешённые находки |
|---|---|---|---|---|---|
| 01-flour | writing v1 | принято 0/3; drafted 3 | — | — | — |
| 02-starter | planned, плана нет | — | — | — | — |

Ревью уровня серии (план серии и серия целиком): 0, устаревших: 0
```

«Нерешённые находки серии» — это находки из журнала серии, то есть ревью плана серии и серии целиком. Находки статей видны в последней колонке таблицы.

Затем проверим, что таблица утверждений совпадает с данными:

```bash
gr claims verify --plan 01-flour/plan.md
```

```
{ "status": "passed", "claims": 14, "drift": [], "missing": [], "invalid": [], … }
```

Если поменять число в `bake.csv`, утверждение попадёт в `drift` — расхождение таблицы утверждений с данными. Проверка не пройдёт, пока таблицу не пересоберут (`claims build`) и не поправят тексты с этим числом.

### Шаг 5. Проверка раздела скриптом

Как только раздел написан, `granki-section` запускает его проверку:

```bash
gr check --plan 01-flour/plan.md --section 01-results.md
```

```
{
  "status": "failed",
  "section": "01-results.md",
  "sha256": "740b3dca…",
  "failed": ["numbers"],
  "checks": [
    { "name": "numbers", "status": "failed", "occurrences": 9, "integers": true,
      "untraced": [ { "section": "01-results.md", "number": "2,2" } ] },
    { "name": "claims", "status": "passed", … },
    { "name": "caveats", "status": "passed", "found": { "C2": "marker" }, … },
    …
  ]
}
```

В тексте сказано «выросло в 2,2 раза», а в данных пшеничная мука после 12 часов поднялась в 2,1 раза. Скрипт нашёл число, у которого нет опоры в таблице утверждений. Оговорка C2 найдена по метке. `sha256` — хеш текста раздела, он понадобится на следующем шаге.

Исправим опечатку, проверим снова и запишем правку в хронологию:

```bash
perl -pi -e 's/\Qвыросло в 2,2 раза\E/выросло в 2,1 раза/' 01-flour/sections/01-results.md
gr check --plan 01-flour/plan.md --section 01-results.md | grep '"status"' | head -1
gr journal log --journal 01-flour/journal.md --actor агент --target 01-results.md --action "исправлено 2,2 → 2,1 по B-wheat-12-rise"
```

```
  "status": "passed",
```

Числа сверяет скрипт, агенты проверяют смысл.

### Шаг 6. Ревью раздела и решение по находкам

`granki-review` запускает для раздела независимые линзы: проход редактуры, опору на данные и свежего читателя. Каждая линза пишет отчёт в `reviews/`, а находки уходят в журнал статьи. Сыграем роль линзы редактуры. Отчёт хранит хеш проверенного текста: когда текст изменится, `status.py` поймёт, что ревью проверяло старую версию.

```bash
cd 01-flour
mkdir -p reviews
SHA=$(gr check --plan plan.md --section 01-results.md | python3 -c "import json,sys; print(json.load(sys.stdin)['sha256'])")
cat > reviews/section-01-results-editorial-2026-11-21-1600.md <<EOF
---
scope: section
target: 01-results.md
reviewed_sha: $SHA
date: 2026-11-21
lens: editorial
findings: []
---

Проход редактуры по разделу 01. Главное: читатель может сложить проценты и удивиться, что вышло больше ста.
EOF
cat > "$WORK/findings.json" <<'EOF'
[
  {"target": "01-results.md", "where": "абз. 1", "severity": "критично", "kind": "спорная",
   "before": "«Её же отметили 75% гостей.»",
   "after": "«Её отметили 75% гостей. Отмечать можно было несколько буханок, поэтому проценты не складываются в сотню.»",
   "rule": "свежий читатель: проценты без пояснения, как голосовали"},
  {"target": "01-results.md", "where": "абз. 1, последнее предложение", "severity": "обычно", "kind": "бесспорная",
   "before": "«Цельнозерновая оказалась посередине: 1,7 раза и 50% голосов.»",
   "after": "«Цельнозерновая оказалась посередине: поднялась в 1,7 раза, её выбрали 50%.»",
   "rule": "проход «предложение»: телеграфный обрывок"},
  {"target": "01-results.md", "where": "абз. 3", "severity": "обычно", "kind": "вопрос",
   "before": "«Короткая расстойка проиграла у всех трёх видов муки.»",
   "after": "[нужно от автора: при какой температуре стояло тесто]",
   "rule": "опора на данные: условие, без которого результат не повторить"}
]
EOF
gr journal add --journal journal.md --source reviews/section-01-results-editorial-2026-11-21-1600.md --findings "$WORK/findings.json"
```

```
{ "status": "passed", "journal": "journal.md", "added": ["N001", "N002", "N003"],
  "review_updated": "reviews/section-01-results-editorial-2026-11-21-1600.md" }
```

ID находок записались в журнал и в поле `findings:` отчёта. Агент показывает находки, критичные первыми, и спрашивает:

> Нашёл три замечания к разделу 01, одно критичное (N001: проценты без пояснения, как голосовали). Что делаем?
> 1. Применить все.
> 2. Обсудить по одной.
> 3. Применить только критичные.
> 4. Записать и отложить.

Автор выбирает третий вариант. N001 касается условия измерения, поэтому даже при этом варианте агент не правит текст молча, а отдельно спрашивает автора. Автор соглашается. Агент правит текст, запускает проверку и записывает решения в журнал. N002 и вопрос N003 получают статус `deferred`: вопрос без ответа автора применить нельзя.

```bash
gr journal log --journal journal.md --actor автор --action "решение по находкам N001–N003: вариант 3"
perl -pi -e 's/\QЕё же отметили 75% гостей.\E/Её отметили 75% гостей. Отмечать можно было несколько буханок, поэтому проценты не складываются в сотню./' sections/01-results.md
gr check --plan plan.md --section 01-results.md | grep '"status"' | head -1
gr journal set --journal journal.md --id N001 --status applied --actor автор --note "вариант 3, согласовано отдельно"
gr journal set --journal journal.md --id N002,N003 --status deferred --actor автор --note "вариант 3: только критичные"
gr plan section --plan plan.md --file 01-results.md --set agent-reviewed
```

В новой фразе «в сотню» написано словами. Слова вместо чисел скрипт не видит, их проверяют линзы. Если бы правка добавила число, например «больше 100%», ему понадобилась бы опора: утверждение в таблице или запись в `numbers.allow` плана.

### Шаг 7. Приёмка разделов

Теперь раздел читает автор. Агент раскладывает замечания автора на четыре группы:
- понятная правка — агент правит сам;
- вопрос — агент задаёт его автору;
- утверждение автора — агент сверяет его с источником;
- новое правило голоса — агент дописывает его в редполитику.

Когда замечаний не осталось, автор принимает раздел:

```bash
gr plan section --plan plan.md --file 01-results.md --set accepted --actor автор
```

```
{ "status": "passed", "section": "01-results.md", "from": "agent-reviewed", "to": "accepted",
  "accepted_sha": "…" }
```

Отложенные обычные находки приёмке не мешают. Её блокируют только открытые находки, отложенные критичные и пометки `[нужно от автора]`. В разделе 02 такая пометка есть:

```bash
gr plan section --plan plan.md --file 02-advice.md --set accepted --actor автор
```

```
{ "status": "error",
  "reason": "02-advice.md cannot be accepted: the text still has [нужно от автора: …]. Resolve them, or pass --force when the author accepts anyway" }
```

Скрипт защищает от случайной приёмки, но не проверяет, кто её делает: `--actor автор` — просто подпись в журнале. Принимать разделы — правило процесса для автора, и скиллы его соблюдают.

Агент спрашивает автора, советовать ли ржаную муку, и вписывает ответ. Ревью разделов 00 и 02 ничего не нашло: пустой список находок записывается в хронологию как «ревью без находок». После этого автор принимает оба раздела.

```bash
perl -pi -e 's/\Q[нужно от автора: советовать ли ржаную муку, если её любят за вкус, а не за подъём]\E/если любишь плотный хлеб с кислинкой, бери её и не жди от неё высоты/' sections/02-advice.md
grep -c "нужно от автора" sections/02-advice.md
gr journal log --journal journal.md --actor автор --target 02-advice.md --action "ответ про ржаную муку вписан в текст"
echo '[]' > "$WORK/empty.json"
for f in 00-intro 02-advice; do
  SHA=$(gr check --plan plan.md --section $f.md | python3 -c "import json,sys; print(json.load(sys.stdin)['sha256'])")
  printf -- '---\nscope: section\ntarget: %s.md\nreviewed_sha: %s\ndate: 2026-11-21\nlens: editorial\nfindings: []\n---\n\nЗамечаний нет.\n' $f $SHA \
    > reviews/section-$f-editorial-2026-11-21-1610.md
  gr journal add --journal journal.md --source reviews/section-$f-editorial-2026-11-21-1610.md --findings "$WORK/empty.json" | grep '"status"'
  gr plan section --plan plan.md --file $f.md --set agent-reviewed | grep '"to"'
  gr plan section --plan plan.md --file $f.md --set accepted --actor автор | grep '"to"'
done
gr status --series ../series-plan.md --format md | grep 01-flour
```

```
0
…
| 01-flour | writing v1 | принято 3/3; accepted 3 | — | — | 2 (критичных 0) |
```

`0` означает, что пометок в разделе не осталось. Две нерешённые находки — это отложенные N002 и N003. Они дождутся следующей сессии.

### Шаг 8. Ревью статьи

Когда все разделы приняты, статья переходит в `article-review`. Скрипт проверяет её целиком: объём, все обязательные оговорки, числа во всех разделах.

```bash
gr plan status --plan plan.md --set article-review | grep '"to"'
gr check --plan plan.md | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['status'], [c['name'] for c in d['checks']])"
```

```
  "to": "article-review"
passed ['plan-sections', 'length', 'numbers', 'claims', 'caveats', 'links', 'public', 'figures', 'published-lock']
```

Затем работают линзы уровня статьи: переходы и повторы между разделами, донесён ли тезис, оговорки и оверклейм. Отдельно проходит фокус-группа читателей: в комнате `granki-reader-panel` Практик, Скептик, Новичок и Сторонник проверенного метода читают статью независимо, каждый своим субагентом. Находки привязываются к разделам и возвращают на доработку только эти разделы.

Линза структуры заметила повтор: правка N001 повторяет то, что уже сказано во вступлении. Автор решает оставить повтор: у процентов читатель уже забудет, как голосовали. Находку отклоняют, и раздел остаётся принятым.

```bash
SHA=$(gr check --plan plan.md | python3 -c "import json,sys; print(json.load(sys.stdin)['sha256'])")
printf -- '---\nscope: article\nreviewed_sha: %s\ndate: 2026-11-21\nlens: structure\nfindings: []\n---\n\nПереходы на месте, тезис донесён. Один повтор между разделами.\n' $SHA \
  > reviews/article-01-flour-structure-2026-11-21-1700.md
cat > "$WORK/article.json" <<'EOF'
[{"target": "01-results.md", "where": "абз. 1", "severity": "обычно", "kind": "спорная",
  "before": "«Отмечать можно было несколько буханок»",
  "after": "[убрать: то же сказано в 00-intro.md]",
  "rule": "структура: повтор между разделами"}]
EOF
gr journal add --journal journal.md --source reviews/article-01-flour-structure-2026-11-21-1700.md --findings "$WORK/article.json" | grep -A1 '"added"'
```

```
    "N004"
```

HTML собирается только по просьбе автора. Для этого шага нужен Pandoc.

### Шаг 10. Правка опубликованной статьи

Через неделю автор решил поправить фразу в совете. Попробуем изменить опубликованный раздел напрямую:

```bash
perl -pi -e 's/\QЕсли печёшь на пшеничной муке\E/Если печёшь из пшеничной муки/' 01-flour/sections/02-advice.md
gr check --plan 01-flour/plan.md | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['status'], [c for c in d['checks'] if c['name']=='published-lock'])"
```

```
failed [{'name': 'published-lock', 'status': 'failed', 'applies': True, 'changed': ['02-advice.md'],
         'hint': 'switch the article to "revising" before editing a published version'}]
```

Опубликованный текст защищён. Правильный порядок другой: вернуть текст, начать новую версию и только потом править. Правка принятого раздела возвращает его в `drafted`, и автор принимает его заново.

```bash
perl -pi -e 's/\QЕсли печёшь из пшеничной муки\E/Если печёшь на пшеничной муке/' 01-flour/sections/02-advice.md
gr plan revise --plan 01-flour/plan.md --actor автор
perl -pi -e 's/\QЕсли печёшь на пшеничной муке\E/Если печёшь из пшеничной муки/' 01-flour/sections/02-advice.md
gr plan section --plan 01-flour/plan.md --file 02-advice.md --set drafted | grep '"to"'
gr journal log --journal 01-flour/journal.md --actor агент --target 02-advice.md --action "версия 2: правка формулировки в первом предложении"
gr check --plan 01-flour/plan.md | grep '"status"' | head -1
gr status --series series-plan.md --format md | grep 01-flour
```

```
{ "status": "passed", "plan": "01-flour/plan.md", "version": 2 }
  "to": "drafted",
  "status": "passed",
| 01-flour | revising v2 | принято 2/3; accepted 2, drafted после правки 1 | 02-advice.md | section-02-advice-editorial-2026-11-21-1610.md | 2 (критичных 0) |
```

Статус показывает три вещи. Раздел 02 снова в работе. Его текст отличается от принятого. Ревью раздела устарело, потому что проверяло прежний текст. Дальше раздел проходит обычный цикл: ревью, приёмку, ревью статьи, `ready`, `publish`. Версия 2 получит свою запись в плане.

**Если поменялись данные, а не текст.** Допустим, выяснилось, что пшеничную буханку после 12 часов отметили не 9 гостей, а 8. `impact.py` ничего не меняет, а показывает, какие разделы задеты и что можно сделать:

```bash
gr impact --series series-plan.md --claim B-wheat-12-liked
```

```
{ "articles": [ { "article": "01-flour", "status": "revising",
    "affected_sections": [ { "section": "01-results.md", "reasons": [ { "claim": "B-wheat-12-liked", "how": "declared" } ] } ],
    "options": […] } ], … }
```

Неопубликованная статья просто правится. Для опубликованной автор выбирает один из вариантов:
- выпустить новую версию;
- записать расхождение в план серии и не трогать статью;
- оставить как есть с причиной.

### Шаг 11. Следующая сессия

Агент не помнит прошлую сессию, всё лежит в журналах. Главред начинает с того, что ищет нерешённые находки во всей серии:

```bash
gr journal list --series series-plan.md | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['pending_total']); [print(f['id'], f['status'], f['severity'], f['kind'], f['target'], 'цитата на месте' if f['still_present'] else 'цитаты уже нет') for j in d['journals'] for f in j['findings']]"
```

```
2
N002 deferred обычно бесспорная 01-results.md цитата на месте
N003 deferred обычно вопрос 01-results.md цитата на месте
```

`still_present` показывает, остался ли в разделе фрагмент, который цитирует находка. Если текст уже переписан, агент не применяет находку вслепую, а показывает её автору. Отклонённая N004 в список не попала: решение по ней принято.

Хронология статьи — в `01-flour/journal.md`: каждое действие, кто его сделал и когда.
