# Процесс: уровни, циклы и статусы

Нормативное описание процесса. Роли и комнаты — в [roles.md](roles.md), файлы и скрипты — в [architecture.md](../dev/architecture.md).

## 1 Шесть уровней работы

| # | Уровень | Артефакт | Что можно сделать | Кто закрывает |
|---|---|---|---|---|
| 1 | План серии | `series-plan.md` | Обсудить, перестроить, добавить или убрать статью | автор |
| 2 | План статьи | `NN-slug/plan.md` | Обсудить, переставить, разбить или объединить разделы | автор |
| 3 | Раздел | `NN-slug/sections/NN-*.md` | Обсудить и поправить один раздел | автор |
| 4 | Ревью раздела агентами | `reviews/section-NN-…-<линза>-<дата>.md` | Триаж замечаний по разделу | Автор принимает раздел |
| 5 | Ревью статьи целиком | `reviews/article-…-<линза>-<дата>.md` | Находки привязаны к разделам и переоткрывают только их | автор |
| 6 | Ревью серии целиком | `reviews/series-…-<линза>-<дата>.md` | Находки по статьям с учётом статуса публикации | автор |

До первого уровня проводятся интервью автора (`author-notes.md`) и подготовка материалов (`shared/evidence/`). Они питают все уровни; см. [architecture.md](../dev/architecture.md#агент-и-скиллы).

**Порядок участия:**
- **Планы:** сначала обсуждение с автором, затем ревью агентами. Замысел и структуру задаёт автор, агенты проверяют уже согласованный план по данным.
- **Текст:** сначала ревью агентами, затем автор. Агенты заранее убирают ошибки в числах, телеграфность и жаргон, и автор читает текст, где осталось только содержание.

## 2 План отдельно от реализации

**План пишется для человека.** Скрипты читают только фронтматтер плана. Тело плана Автор читает в редакторе или в HTML, обсуждает с агентом и перестраивает.

План серии содержит:
- читателя и решение, которое он принимает;
- жанр и то, что серия не делает, например «обзор результатов, не руководство по воспроизведению»;
- список статей: по абзацу о каждой и статус;
- распределение тем между статьями, чтобы не было повторов;
- общие обязательные оговорки и глоссарий;
- правила публичности.

План статьи — это вопрос читателя, тезис и разделы. Каждый раздел описан так:
- назначение: какой вопрос читателя закрывает;
- 3–6 тезисов;
- опоры короткими ссылками на таблицу утверждений, например `[R0007]`;
- рисунок или таблица с требованиями: числа на столбцах, подписи, размеры моделей;
- обязательные оговорки с ID;
- переход к следующему разделу;
- примерный объём, без жёсткого лимита.

**Цикл плана** одинаков для плана серии и плана статьи:

```
черновик → (обсуждение с автором ↺) → ревью агентами → (решения автора по находкам) → утверждён
```

Статусы: у плана серии `draft → approved`, у статьи `plan-draft → plan-approved`. Ревью плана отдельного статуса не имеет: оно видно по отчётам `reviews/plan-…` и `reviews/series-plan-…` и по находкам в журнале.

1. **Черновик.** Агент готовит план по интервью автора и материалам.
2. **Обсуждение с автором.** Автор читает план, обсуждает и перестраивает его с агентом. По желанию открывается «Планёрка серии» или «Планёрка статьи». Цикл повторяется, пока у автора есть замечания.
3. **Ревью агентами.** Линзы: методология и опора на данные, ценность для читателя, структура и повторы, публичность; для плана серии — ещё лишняя сложность. Спорные находки обсуждает «Совет по находкам».
4. **Утверждение.** Автор решает по находкам, по одному вопросу, и утверждает план.

**Реализация читает план, но не меняет его.** Раздел пишется по своей записи в плане. На вход идут таблица утверждений, `author-notes.md`, редполитика и краткое содержание соседних разделов. Если при письме выясняется, что раздел надо строить иначе, агент предлагает правку плана, а не перестраивает раздел молча.

**Перестройка плана после написания.** Агент показывает, какие написанные разделы задеты. Для изменений по утверждениям и терминам он опирается на `impact.py`. После согласия автора задетые разделы переводятся в `needs-rework` (`plan.py section`), остальные остаются принятыми.

## 3 Цикл раздела

```
planned → drafted → agent-reviewed → (обсуждение с автором ↺) → accepted
              ↑______ needs-rework: правка плана, ревью статьи или серии ______|
```

1. **Написать.** Раздел пишется по записи плана. Сразу после этого `check.py --section` проверяет в этом разделе числа прозы, утверждения, метки оговорок, ссылки и публичность. Поячеечная сверка таблиц с CSV запланирована.
2. **Ревью раздела агентами.** Линзы: числа и оверклейм, голос автора, проза (проходы редактуры), «свежий читатель раздела» (закрывает ли раздел своё назначение из плана). Результат — файл ревью: у каждой находки есть ID, важность (критично или обычно), вид (бесспорная или спорная) и статус. Дальше агент показывает находки и спрашивает, что с ними делать (см. «Решение по находкам» ниже).
3. **Обсудить с автором.** Автор читает раздел после решения по находкам вместе со списком открытых находок и даёт замечания пакетом. Агент раскладывает их на четыре группы:
   - понятно, правлю;
   - вопрос к автору, по одному, с вариантами и рекомендацией;
   - утверждение автора, сверяю с источником;
   - новое правило голоса, дописываю в редполитику.

   Цикл повторяется, пока у автора есть замечания. После правок скрипт проверки запускается снова. По желанию можно открыть комнату «Разбор раздела».
4. **Принять.** Автор закрывает раздел. В фронтматтер плана записывается SHA принятого текста.

## 4 Ревью статьи и серии

**Статья.** Запускается, когда все разделы приняты. Что проверяется:
- переходы и повторы между разделами;
- донесён ли тезис;
- единство терминов и чисел;
- расстановка оговорок;
- объём;
- оверклейм на уровне всей статьи.

Отдельно работает фокус-группа читателей. Каждая находка привязана к разделу и переоткрывает только его.

**Серия.** Что проверяется:
- одинаковые числа и термины во всех статьях;
- повторы и распределение тем;
- перекрёстные ссылки;
- выполнены ли обещания вида «в одной из следующих статей разберу».

Находки по опубликованным статьям идут по правилам раздела 6, принятые расхождения не считаются новыми находками.

**Порядок любого ревью:** ревью статьи и серии проверяет текст, поэтому агенты идут первыми, а автор решает по триажу. Сначала скрипт, затем независимые линзы, каждая пишет свой файл. Спорные находки обсуждает «Совет по находкам». Находки всех линз попадают в реестр журнала статьи `journal.md` со сквозными ID; решения по ним описаны ниже.

**Решение по находкам** одинаково для любого ревью. Агент выводит находки, критичные первыми, и предлагает четыре варианта:
1. применить все;
2. обсудить по одной;
3. применить только критичные;
4. записать и отложить.

При первом и третьем вариантах находки, которые затрагивают число, условие измерения, вывод или оговорку, агент всё равно разбирает с автором по одной. Вопрос автору применить нельзя: при третьем варианте он вместе с остальными некритичными находками получает `deferred`. Подробные правила — в [decisions.md](../../skills/granki-review/references/decisions.md). После правок агент запускает проверку и записывает статус каждой находки в журнал. Отложенные находки получают статус `deferred`. В следующей сессии `journal.py list` находит нерешённые находки во всей серии и показывает, есть ли ещё в тексте цитируемый фрагмент. Без человека агент ничего не применяет и откладывает ревью.

**Журнал статьи**. У каждой статьи и у серии есть `journal.md` из двух частей:
- **«Находки»** — единый реестр находок всех ревью со сквозными ID (`N001`, …), важностью, видом, цитатой и статусом;
- **«Хронология»** — записи, которые только дописываются: время, кто (агент, автор или роль), раздел, что сделано.

В хронологию попадает каждое действие: написан или изменён раздел, проведено ревью, добавлены находки, принято решение, автор принял раздел или план. Журнал ведёт скрипт `journal.py`; файл ревью остаётся отчётом с выводом и вопросами и ссылается на ID находок.

**Устаревание.** Каждый отчёт ревью хранит SHA проверенного текста. Если текст изменился, `status.py` помечает ревью устаревшим на всех уровнях выше.

## 5 Статусы статьи

```
planned → plan-draft → plan-approved → writing → article-review → ready → published v1
                                                                            ↓
                                                           revising v2 → published v2
```

| Статус | Значение |
|---|---|
| `planned` | Статья есть в плане серии, плана статьи нет |
| `plan-draft` | План статьи пишется или обсуждается |
| `plan-approved` | Автор утвердил план |
| `writing` | Разделы в работе; статусы разделов — в плане |
| `article-review` | Все разделы приняты, идёт ревью статьи |
| `ready` | Автор принял статью, готова к публикации |
| `published` | Опубликована: версия, дата, ссылка, коммит, хеши разделов и хеш опубликованной страницы записаны в плане (`plan.py publish`) |
| `revising` | Готовится новая версия опубликованной статьи |

Скрипт проверки не пропустит изменение разделов статьи в статусе `published`, пока она не переведена в `revising`.

## 6 Изменения на уровне серии и опубликованные статьи

Новый факт, термин, исправленное число или перестройка серии записываются в журнал серии как изменение. Скрипт `impact.py` строит матрицу «статья → затронутые разделы → статус». По каждой статье решение принимает автор:

| Статус статьи | Варианты |
|---|---|
| Не опубликована | Правим; затронутые разделы уходят в `needs-rework` |
| Опубликована | **(а)** новая версия с пометкой «обновлено» и записью в журнале статьи; **(б)** не трогаем: правка вносится только в неопубликованные статьи, ID утверждения записывается в `known_divergences` плана серии, а причина — в его раздел «Принятые расхождения»; при необходимости следующая статья ссылается на уточнение; **(в)** игнорируем с причиной |

Решение и причина записываются в хронологию журнала серии.

## 7 Правила работы с автором

- Коммит, синхронизация, сборка HTML и PDF выполняются только по команде автора.
- Решения принимаются по одному вопросу: пояснение, варианты, обоснованная рекомендация.
- Факты о работе автора (мотивация, рабочий контекст, происхождение данных, ручная ревизия) берутся только от автора и записываются в `author-notes.md`. Утверждения автора тоже сверяются с источниками, о расхождении сообщается автору, молча оно не правится.
- Агент не вносит формулировок, которых автор не использует. Список «как я говорю и не говорю» в редполитике пополняется после каждого чтения; уровень правила (проект, серия, статья) выбирает автор.
- Редполитика трёхуровневая: общая для проекта, с перекрытием на уровне серии и статьи. Слои накладываются по разделам `##`: тот же заголовок заменяет раздел, `(+)` дописывает, `(-)` убирает. Итог собирает `policy.py`; формат — в [formats.md](../../skills/granki-tools/references/formats.md).
- Рисунок проверяется по отрисованному файлу. При правке файл рисунка получает новое имя.
- Ворота автора: план серии, план статьи, каждый раздел, статья после ревью, решения по ревью серии, публикация.
