# Форматы файлов Granki

Версия схемы: `granki: 1`. Скрипты отказываются работать с файлом без этой строки во фронтматтере.

## Серия: `series-plan.md`

```yaml
---
granki: 1
title: Заварка чая
status: draft                        # draft | approved | writing | done; меняет plan.py series
articles: [01-green, 02-black]      # папки статей в порядке чтения; статья без plan.md считается planned
canon: ../.agents/canon.md          # слой канона проекта
known_divergences: [T-best-share]   # ID утверждений, расхождение которых между статьями принято
html: {brand: Чай, tagline: Опыты на кухне, index_kicker: Серия о чае}
---
```

Тело файла — план серии для человека, скрипты его не читают.

## Канон: три слоя

Канон — редакционные правила: читатель, площадки, регистр, словарь, голос автора. `series-plan.md` указывает канон проекта в поле `canon:` (путь относительно файла серии). Слой серии — `canon.md` рядом с `series-plan.md`, слой статьи — `canon.md` в папке статьи. Оба необязательны.

Файл делится на разделы `##`. В более частном слое:

| Заголовок | Действие |
|---|---|
| `## Название` | заменяет раздел с тем же названием |
| `## Название (+)` | дописывает раздел |
| `## Название (-)` | убирает раздел |
| новый заголовок | добавляет раздел в конец |

`(+)` и `(-)` для раздела, которого нет в верхних слоях, `canon.py` выполняет как новый раздел или пропускает и сообщает в `warnings`. Итог собирает `canon.py`.

Стандартные разделы — из шаблона `assets/templates/canon.md`: «Проект и читатель», «Площадки и форматы», «Регистр и тональность», «Словарь: запрещено/принято», «Фактура: на что опираемся», «Примеры голоса», «Как я говорю и не говорю», «Открытые вопросы». Остальные шаблоны тоже лежат в `assets/templates/` этого скилла.

## Статья: `NN-slug/plan.md`

```yaml
---
granki: 1
title: Зелёный чай
status: writing        # planned | plan-draft | plan-approved | writing | article-review | ready | published | revising
version: 1
description: Одна фраза для указателя статей
root: .                # корень статьи относительно plan.md
sections_dir: sections # где лежат разделы NN-*.md
length: {min: 12000, max: 21000, strict: false}   # необязательно; знаки прозы без таблиц, кода и комментариев; без strict выход за границы — предупреждение
claims: [data/claims.csv]
data_dirs: [data, ../shared/data]  # где искать CSV и JSON из локаторов
numbers: {decimal: ",", renderers: ["percent:2", "fixed:2"], allow: ["2,5"], integers: false}
caveats:
  C1: {text: Пробовали один сорт чая, pattern: null}
required_caveats: [C1]
public: {forbidden: ['секретн'], allow_external_links: false, assets_dir: assets}
figures: {manifest: assets/*manifest.json}
sections:
  - {file: 00-intro.md, status: accepted, accepted_sha: <sha256>, caveats: [C1], claims: []}
  - {file: 01-results.md, status: drafted, claims: [T-best-share]}
published:
  - {version: 1, date: 2026-01-01, url: https://…, commit: <git>, html_sha256: <sha256>, sections: {00-intro.md: <sha256>}}
---
```

Статусы раздела: `planned`, `drafted`, `agent-reviewed`, `accepted`, `needs-rework`. Проверка статьи (`check.py --plan`) работает и до первого раздела: записи `planned` без файла попадают в `not_written`, а не в `missing_files`.

Статусы меняет `plan.py`, а не правка руками. Скрипт переписывает только фронтматтер (комментарии YAML в нём не сохраняются), тело плана не трогает и пишет каждое изменение в хронологию журнала. Переходы статьи:

```
planned → plan-draft → plan-approved → writing → article-review → ready → published → revising
```

Раздел записывается в план командой `plan.py entry --plan … --file … [--caveats …] [--claims …] [--after …]`; оговорки сначала описываются в `caveats:`. Принять раздел (`plan.py section --plan … --file … --set accepted`) нельзя, пока в тексте есть `[нужно от автора: …]` или по разделу есть открытые (`open`) или отложенные критичные находки. Обычные отложенные находки приёмке не мешают; `--force` принимает всё равно и пишет это в журнал. Допустимы и возвраты: `plan-draft → planned`, `plan-approved → plan-draft`, `writing → plan-draft`, `article-review → writing`, `ready → article-review | writing`, `revising → article-review | ready | writing`. В `article-review` статья переходит, только когда все разделы приняты и после приёмки не менялись. В `published` — только командой `publish`, в `revising` — командой `revise`. Остальное возможно лишь с `--force`, и это отмечается в журнале.

## Разделы

Файлы `NN-имя.md` в `sections_dir`. Две цифры задают порядок и должны быть уникальны. Первый раздел начинается с заголовка первого уровня — это название статьи. Ссылки на рисунки идут относительно папки разделов и указывают внутрь `assets_dir`, например `../assets/chart.png`.

Обязательная оговорка помечается меткой перед её формулировкой, в том же абзаце. После метки должно идти не меньше трёх слов оговорки, иначе метка не засчитывается (`markers_without_text`). Метки внутри блоков кода не считаются.

```markdown
<!-- caveat:C1 --> Пробовал только один сорт, поэтому выводы скромные.
```

`pattern` в описании оговорки нужен только для статей, перенесённых без меток: тогда оговорка ищется по регулярному выражению. Проверка статьи требует все оговорки из `required_caveats` и из записей разделов. Проверка одного раздела требует только оговорки, закреплённые за ним в `sections[].caveats`.

## Числа

Проверяются числа прозы: без таблиц, блоков кода (```` ``` ```` и `~~~`) и комментариев. Таблицы пока не сверяются поячеечно.

- Десятичные числа (`87,50`, `12 500,75`) проверяются всегда.
- Целые из двух и более цифр (`24`, `2026`) проверяются при `numbers.integers: true`. Числа внутри названий (`Qwen3`, `27B`, `2.6`) не считаются.

Каждое число должно совпасть с одной из форм какого-нибудь утверждения или стоять в `numbers.allow`. Формы задают `renderers`: `percent:N` — значение ×100 с N знаками, `fixed:N` — значение с N знаками. Для целых добавляются формы `fixed:0` и `percent:0`. Округление принимается и «половина вверх», и по правилам Python. Слова вроде «в три раза» скрипт не видит: правка, которая вводит или меняет число, всегда спорная.

## Таблица утверждений

CSV с колонками `ID,formulation,value,source`. Источник — локатор одной ячейки:

| Локатор | Значение |
|---|---|
| `file.csv: key=value; column=col` | строка, где `key` равно `value` |
| `file.csv: a=1; b=2; column=col` | несколько условий; так их пишет `claims.py build`, допустима и запись `a=1,b=2` |
| `file.csv: row=N; column=col` | N-я строка таблицы, считая заголовок первой; пустые строки не считаются |
| `file.json#/a/0/b` | значение по JSON Pointer |
| `derived: описание` | производное значение; скрипт его не сверяет и показывает в `unverifiable` |

Источник, который не разбирается как локатор (опечатка в колонке, нет `column=`), — ошибка `invalid`: проверка проваливается. Повторяющиеся ID — тоже ошибка. `claims.py build` перезаписывает только строки, которые порождают правила; ручные и `derived:` строки сохраняются.

`claims.py build` строит таблицу по правилам `claims_build` в плане:

```yaml
claims_build:
  - source: tasting.csv
    key: cup                        # колонка для локатора или список [cup, minutes]; без неё — row=N
    where: {temperature: "80"}      # необязательный фильтр
    id: "T-{cup}-{column}"
    formulation: "{cup}: {column}"
    columns: [share, minutes]
```

## Принятые расхождения

`known_divergences` в плане серии делает две вещи:
- снимает конфликт одинаковых ID с разными значениями между статьями (`series-claims`);
- в опубликованной статье переводит расхождение утверждения с данными из провала в отчёт (`accepted_divergences`).

В неопубликованной статье расхождение с данными остаётся провалом: её нужно поправить.

## Журнал статьи: `journal.md`

У каждой статьи (и у серии, для ревью серии) есть журнал. Его создаёт и дописывает `journal.py`; руками его не правят. Журнал и папка `reviews/` лежат рядом с `plan.md`, даже если `root` плана указывает на тексты в другом месте. Блокировки записи хранятся во временном каталоге системы, а не в репозитории.

```markdown
# Журнал

## Находки

| ID | Дата | Источник | Раздел | Где | Важность | Вид | Было | Стало | Правило | Статус |
|---|---|---|---|---|---|---|---|---|---|---|
| N001 | 2026-01-01 | reviews/section-01-results-editorial-2026-01-01-1405.md | 01-results.md | абз. 1 «Лучше всего» | критично | спорная | «…» | «…» | проход 4 | open |

## Хронология

- 2026-01-01 14:05 · агент · 01-results.md · добавлено находок: 3 (N001–N003) из reviews/section-01-results-editorial-2026-01-01-1405.md
- 2026-01-01 14:20 · автор · N003 → rejected: автор против
```

- ID сквозные внутри журнала: `N001`, `N002`, … в журнале статьи и `S001`, … в журнале серии.
- `Раздел` — файл раздела. Для находки к плану статьи — `plan.md`. В журнале серии раздел пишется как `статья/файл`, а находка к плану серии — как `series-plan.md`.
- `Важность`: `критично` или `обычно`. `Вид`: `бесспорная`, `спорная` или `вопрос`: вопрос автору, ответ на который может изменить текст.
- `Статус`: `open`, `deferred`, `applied`, `rejected`, после статуса допустима пометка в скобках. Нерешённые — `open` и `deferred`.
- В `Было` текст раздела цитируется в «ёлочках»; цитат может быть несколько. `journal.py list` проверяет, все ли они ещё есть в разделе: `still_present`. В `Стало` действие без готового текста пишется в квадратных скобках: `[перенести в конец абзаца 5]`.
- В хронологию попадает каждое действие: написан или изменён раздел, проведено ревью, принято решение, автор принял раздел или план.

Находки для `journal.py add` передаются JSON-списком объектов. Обязательные ключи: `target`, `severity`, `kind`, `before`, `after`; `where` и `rule` желательны. Для вопроса в `after` пишется `[нужно от автора: …]`. Пустой список записывает в хронологию «ревью без находок».

## Ревью

Файлы `reviews/<уровень>-<цель>-<линза>-YYYY-MM-DD-HHMM.md` в папке статьи или серии (например `section-01-results-editorial-…`, `article-01-green-structure-…`, `plan-01-green-evidence-…`, `series-plan-tea-fresh-reader-…`, `series-tea-series-…`) — отчёт линзы: вывод и итог проверки. Сами находки, в том числе вопросы автору, и их статусы хранятся только в журнале. `journal.py add --source reviews/<отчёт>` сам дописывает ID в `findings:` отчёта. Фронтматтер:

```yaml
---
scope: section          # section | article | plan | series | series-plan
target: 01-results.md   # для раздела
reviewed_sha: <sha256 текста, который проверялся>
date: 2026-01-01
lens: editorial
findings: [N001, N002, N003]   # ID находок в журнале
---
```

Состояние ревью в `status.py`:
- `current` — текст не менялся;
- `processed` — текст менялся, но открытых находок ревью не осталось (применены, отклонены или отложены);
- `stale` — текст менялся, а находки ревью ещё открыты, или ревью не нашло ничего и после него текст правили.

Хеши:
- раздел — его файл;
- статья — разделы, собранные в один текст;
- план (`plan`, `series-plan`) — тело плана без фронтматтера, поля `plan_sha256` и `series_plan_sha256` в выводе `status.py`;
- серия — строки `папка:хеш статьи` в порядке `articles`.
